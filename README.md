# telegram-support-system

Служба поддержки в Telegram: пользователь пишет боту → сообщение попадает в очередь → оператор видит чат в miniapp, берёт его в работу (claim/lock) и отвечает.

Три независимых сервиса:
- `apps/api` — FastAPI + SQLite. Хранит чаты, сообщения, статусы, назначения операторов.
- `apps/bot` — Telegram-бот (aiogram), пересылает сообщения между пользователем и API.
- `apps/miniapp` — Telegram Mini App (статический HTML/JS) для операторов: список чатов, claim/release/close, переписка.

## Как это работает

- Статусы чата: `open` (новый) → `in_progress` (взят оператором) → `closed`.
- **Claim/lock**: взять чат в работу может только один оператор. Если чат уже взят — второй получит `409 Conflict`. Проверено атомарным `UPDATE ... WHERE assigned_operator_id IS NULL` на уровне БД.
- Отвечать в чате может только тот оператор, который его взял.
- **Доступ к miniapp**: проверяется подпись Telegram WebApp `initData` + список разрешённых `OPERATOR_IDS`. Без обоих условий — 401/403, публичного доступа нет.

## Запуск локально

### 1. Переменные окружения

Скопируйте `.env.example` в `.env` в корне репозитория и заполните:

```
cp .env.example .env
```

- `BOT_TOKEN` — токен от [@BotFather](https://t.me/BotFather).
- `OPERATOR_IDS` — ваш Telegram ID (узнать можно у [@userinfobot](https://t.me/userinfobot)) и ID остальных операторов, через запятую.
- `DEV_MODE=1` — оставьте включённым для локального теста miniapp вне Telegram (см. ниже).

### 2. Запуск через docker-compose

```
docker-compose up --build
```

Поднимутся:
- API — `http://localhost:8000`
- Bot — запускает long polling, отдельного порта наружу не публикует
- Miniapp — `http://localhost:3000`

### 3. Проверка сквозного сценария

1. Откройте бота в Telegram, отправьте `/start`, затем любое сообщение.
2. Откройте `http://localhost:3000` в браузере.
   - Если открываете **не из Telegram** (обычный браузер) — при первой загрузке появится запрос "Введите ваш Telegram ID для DEV-режима". Введите ID из `OPERATOR_IDS`. Это работает только при `DEV_MODE=1` на API — не включайте DEV_MODE в проде.
   - Если открываете **как настоящий Telegram Mini App** (кнопка меню бота со ссылкой на miniapp) — авторизация пройдёт автоматически через `initData`, `DEV_MODE` не нужен.
3. Сообщение появится во вкладке "Открытые". Нажмите "Взять в работу" — чат переходит в "В работе".
4. Напишите ответ — он придёт пользователю в Telegram.
5. "Закрыть чат" — чат уходит во вкладку "Закрытые". Новое сообщение от пользователя снова открывает чат.

### Проверка claim/lock (без пересечений)

Откройте miniapp в двух разных браузерах (или в обычном + в режиме инкогнито) под разными `OPERATOR_IDS`. Оба увидят один и тот же открытый чат. Кто нажмёт "Взять в работу" первым — получит чат; второй увидит алерт "Этот чат уже взят в работу другим оператором".

## Продакшн-деплой (Render + Vercel, как в этом проекте)

- `apps/api` и `apps/bot` — два отдельных Web Service на [Render](https://render.com), каждый со своим `Dockerfile`.
  - На сервисе API задайте `BOT_TOKEN` (для проверки подписи initData) и `OPERATOR_IDS`. `DEV_MODE` не задавайте (по умолчанию выключен).
  - На сервисе бота задайте `BOT_TOKEN` и `API_URL` (адрес сервиса API на Render).
- `apps/miniapp` — статический сайт на [Vercel](https://vercel.com) (корень проекта — `apps/miniapp`). Внутри `index.html` в константе `API` укажите реальный адрес вашего API-сервиса на Render.
- В [@BotFather](https://t.me/BotFather) настройте Menu Button / Web App с адресом вашего miniapp на Vercel — тогда операторы будут открывать его прямо из чата с ботом, с автоматической `initData`-авторизацией.

### Известные ограничения (осознанно, для тестового задания)

- SQLite-файл на Render free tier не персистентный между полными редеплоями (эфемерная файловая система) — для продакшна потребуется постоянный диск или переход на управляемую БД.
- Обновления в miniapp — через polling (раз в 3 секунды), не WebSocket/SSE.
